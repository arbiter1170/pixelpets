# Walklings smoke tests

Small browser checks so a later change can show the game still boots on a phone width. Players never load this folder. There is no GitHub Actions workflow yet: run the suite locally. A new spec also gets a row in this file, and the status docs follow `.cursor/skills/walklings-docs/SKILL.md`. The Oct 14 documentation audit added no spec. Recording the town-board calls the same day added no spec. TB-1 is covered by `tests/town_board.spec.js`. Scoping modern and arcade controls (Q26) added no spec. `tests/controls.spec.js` covers it: arcade on an old save, every modern button, switching both ways, and the joystick.

## How to run

From a clean clone, in the repo root:

```
npm install
npx playwright install chromium
npm test
```

`npm test` runs `python3 tools/bump_build.py --check` (must exit 0) and then Playwright. `npm run test:agent` runs that same build check, then `node tools/rtdb_rules_test.js` against a local Realtime Database emulator, then Playwright. The rules step and the emulator specs talk only to `127.0.0.1`. `npm run test:agent` gives every run its own free emulator ports, so runs that share a machine never collide: the rules step reads `PP_RTDB_PORT`, `PP_RTDB_HUB_PORT` and `PP_RTDB_LOGGING_PORT`, and `tests/emu_shared.js` reads `PP_EMU_DB_PORT`, `PP_EMU_AUTH_PORT`, `PP_EMU_FS_PORT`, `PP_EMU_FS_WS_PORT`, `PP_EMU_HUB_PORT` and `PP_EMU_LOGGING_PORT` and adds `dbPort`, `authPort` and `fsPort` to each `?cloud=emu` page. Set any of them to pin a port. Plain `npx playwright test` picks its own free emulator ports too, in the Playwright global setup (`tests/emu_setup.js`), and a run's teardown only stops the emulator that run started (the pid file carries `PP_EMU_RUN`); an emulator it did not start stays up. Root `firebase.json` still lists the old fixed ports for manual use. Each emulator runs from its own temp folder with a generated `firebase.json` and the UI off, and `tools/emu_ports.js` stops it and its java child on every exit path. On Windows the runner starts Playwright and the firebase CLI as `node <their JS file>` (the `.bin` and `npx` shims are `.cmd` files that `spawn` cannot run), stops the emulator with `taskkill /T /F`, and needs a `python3.exe` on `PATH` (python.org's installer only creates `python.exe`) and a JDK for the emulator. The browser maps the live Firebase hosts to an address that does not resolve, and `cloud.js` ignores the live config while `navigator.webdriver` is set, so the suite never signs in or writes to project `walklings-4cc89`. The pinned SDK host stays reachable so `?cloud=emu` can load it. Chromium only, one width at a time, against a local static server (`python3 -m http.server`, port 8080). Set `PP_URL` to point at another origin instead, for example the live site:

```
PP_URL=https://arbiter1170.github.io/pixelpets/ npm test
```

When `PP_URL` is set, the config does not start a server. `PP_PORT` changes the local port.

The config runs 2 workers. `fullyParallel` stays false, so the tests in one file still run in order on one worker. Pass `--workers=1` to run everything serially.

It sets `PP_SLOW=1` so that project keeps the `/@w1/` invert and drops `@slow` from it, then passes `--project=390 --grep @slow`. Shared helpers are in `tests/helpers.js`: `starterSave()` (the v2 seed used below), `installSave(page, save)`, `gotoGame(page, query)`, `trackErrors(test, expect)` (the console-error assertion), `boxesOverlap`, `shot(page, name)`, `artifactsDir(sub)` (creates the review-shot folder and returns it; set `PP_ARTIFACTS` to a writable directory when the default one cannot be created), `withOverlay(page, overlay, key)` (adds a fixture `data/detail_*.json` overlay to `MAPDATA` before boot; call it before `gotoGame`), and `playScene(page, choices, onChoice)` (presses Space through plain lines and clicks the labelled choice once `PixelPets.optionsReady` is true; a shop sheet clicks BUY, or X for Not now; returns the prompts it saw), and `newPlayerPicker(page)` (a new game up to the first look picker, WHO ARE YOU?: in the intro, or at the bedroom mirror since PARTNER_DAY; call it after `gotoGame` with no save).

A console message of type `error`, or any uncaught page error, fails the test.

Waiting on state, not on time. A few traps that made tests flaky:

- `page.waitForFunction(fn, arg, options)` takes the options third. `waitForFunction(fn, { timeout: 8000 })` passes the object as `arg`, so the timeout is ignored and the wait runs until the test times out. Write `waitForFunction(fn, null, { timeout: 8000 })`.
- Option buttons (the basket, `#sbName`, `#sbChoices`) ignore taps for 500 ms after they are drawn. Wait for `PixelPets.optionsReady`, and after a tap wait for the step to be used up (the box count or mode changes, or the overlay hides) before looking again. The basket YES wobbles for about 360 ms before `#ovBasket` hides.
- Care bars move on the 1 s care tick, which runs on frame time. Wait for a marker that the same tick writes (the partner's `#valEnergy`, for example), not for a fixed number of seconds.
- The walk camera pans over a few frames after `PixelPets.goto`. Before a map tap, wait until the camera holds still, the tile is inside the canvas and `document.elementFromPoint` there is `#mapCanvas` (a tip on `#tutLayer` can sit on top).
- Pin `PixelPets.battle.rng` when a test needs a move to land. Moves under 100 accuracy miss sometimes.
- The first autosave (5 s after boot) rewrites the seeded save with the game's full key set. Take a save baseline after that write.

## iPhone emulation (WebKit)

Everything above runs on Chromium. A phone plays this game in Safari, which is WebKit, so there is an opt-in lane that runs the same game and specs on Playwright's WebKit with an iPhone profile (viewport, pixel ratio, touch, user agent). It needs no extra packages and no Python (`tools/static_server.js` serves the folder).

```
npx playwright install webkit             # once. Linux also needs: npx playwright install-deps webkit
npm run iphone                            # a window that is the phone: iPhone 14 as Safari shows it (toolbars up), debug on
npm run iphone -- --device "iPhone 16 Pro" --full     # another phone, whole screen (a home-screen web app)
npm run iphone -- --list                  # every phone profile
npm run iphone -- --lan                   # also serve to a real iPhone on the same Wi-Fi; prints the address to type in Safari
npm run iphone -- --url https://arbiter1170.github.io/pixelpets/    # the live site instead of this folder
npm run iphone -- --headless --selftap --shot a.png   # no window: load, print the build, send one tap, print the events, take a picture
npm run test:iphone -- tests/shop_dock.spec.js --project=iphone-14-safari    # the specs, one phone
npm run test:iphone                       # every spec, eight phone sizes (slow: run one spec or one project when you can)
```

`npm run iphone` serves on port 8080, or on any free port if something else already has it (`--port 8090` pins one). It prints every pointer, touch and click event with its id and timestamp (`--no-input-log` turns that off), which is the quickest way to see what the page is really being given. `--trace t.zip` records a Playwright trace to open with `npx playwright show-trace t.zip`. `--engine chromium` runs the same phone on Chromium to compare.

**What this is not.** It is not Apple's iOS Safari. These need the iOS Simulator (Xcode, Mac only) or a real iPhone: the Safari toolbars growing and shrinking while you scroll, safe-area insets (`env(safe-area-inset-*)` is always 0 here), audio unlock, rubber-banding, touch ids, the keyboard pushing the page up. On a Mac, the real iOS engine is one command away: `open -a Simulator`, then `xcrun simctl openurl booted http://localhost:8080/?debug=1` with `node tools/static_server.js` running, and Safari's Develop menu, Simulator, for the console. From a Windows or Linux desktop, use `--lan` and a real iPhone.

**Known differences that fail specs without a bug in the game** (found Oct 28, 2026 on the Linux build of Playwright WebKit; compare against the base commit before calling a WebKit failure new):

- A WebKit `tap()` sends `pointerdown`, `touchstart`, `pointerup`, `touchend` and **no `click`**; Chromium's adds `mousedown` and `click`. Every tap reuses pointer id 2 and touch id 0, where an iPhone gives each touch a new id.
- `guardOverlayOpen` (game.js) swallows the finger that was down when an overlay opened, and a lifted finger stays in its `carried` set until the next overlay opens (a swallowed `touchend` has its default prevented, so no click follows to clear it). A line advances on `pointerdown`, so the next panel always opens under a finger. With one reused id, the next tap, or any mouse click, is swallowed: the starter basket (YES never appears) and so every `intro_cutscene.spec.js` row past the first choice time out. Forgetting a finger when it lifts makes all 12 of those rows pass on WebKit. The game is unchanged: it is a touch-handling change, so it is Vincent's call (AGENTS.md rule 3).
- `page.mouse.wheel` does not exist on mobile WebKit (`map_layers.spec.js:289`).
- The failures already on main on Chromium (T-C6, the `hc_apt_in` zoom row, `map_zoom.spec.js:339`, the dock toast at 320, `shop_p0.spec.js:143`, `modern_hud_rows.spec.js:59`) fail the same way here.
